# Фактическая готовность безопасности

Дата проверки: 01.11.2026. Это инженерная оценка текущего репозитория и публичного стенда,
а не сертификат соответствия и не юридическое заключение. Базовая система требований —
[OWASP ASVS 5.0](https://asvs.owasp.org/), для сессий и TLS — официальные OWASP Cheat Sheets.

## Что реально работает сейчас

| Область | Подтверждённое состояние |
|---|---|
| Транспорт | Публичный стенд работает по HTTPS; включены HSTS, CSP, `frame-ancestors 'none'`, `nosniff`, `no-referrer`, COOP/CORP и ограничительный Permissions-Policy. API слушает только loopback за Caddy. |
| Изоляция пользователей | `user_id` берётся из серверной сессии; IDOR-тест обходит параметризованные OpenAPI-маршруты. |
| Пароли, сессии и секреты | Пароли — Argon2, токен — 32 случайных байта, в БД только SHA-256, есть срок и отзыв. Ошибка входа не раскрывает существование email. Попытки входа ограничены отдельно. Файлы пилотных секретов создаются с правами `0600` в каталоге `0700`. |
| Ответы и логи | Финансовые API-ответы имеют `Cache-Control: no-store`; входные значения не отражаются в ошибках; access log API выключен. |
| Входные данные | Лимит запроса 3 МиБ, CSV — 2 МиБ/20 000 строк, формулы экранируются, SQL строится SQLAlchemy. |
| Жизненный цикл | Экспорт и удаление профиля покрыты тестами. На стенде retention и SQLite backup запускаются systemd-таймером каждые 6 часов. |
| Зависимости | Python audit после обновления `pip` — без известных уязвимостей; npm audit проходит gate с ограниченным и датированным allowlist. |

## Где проходит честная граница

Публичный стенд — демонстрационный контур для синтетических данных. Он **не готов принимать
реальные банковские выписки**, даже если функции импорта технически доступны.

Главные блокеры:

1. Web bearer-токен хранится в `localStorage`. OWASP прямо не рекомендует хранить там
   идентификаторы сессий: любой XSS получает к ним доступ. Нужна серверная web-сессия в
   `HttpOnly; Secure; SameSite=Strict` cookie или BFF; для cookie-запросов — CSRF-защита.
2. SQLite и локальные резервные копии демо-стенда не зашифрованы приложением. Для реальных
   данных нужны зашифрованный диск/том, управляемые ключи, раздельный доступ и проверяемое
   восстановление. Пилотный backup шифруется, но шифрование диска подтверждает оператор.
3. In-memory limiter защищает один процесс и IP, но не учётную запись от распределённого
   credential stuffing. Нужен общий Redis/proxy limiter, счётчик неудач по аккаунту,
   возрастающая задержка и, по риску, MFA.
4. Нет production-процесса мониторинга: централизованного security-аудита, оповещений,
   ротации ключей, incident response и подтверждённых сроков реакции на уязвимости.
5. Реального банковского коннектора нет. Перед Open Banking нужны официальный OAuth/consent
   flow, проверка подписей и сертификатов, минимальные scopes, отзыв доступа и аудит поставщика.
6. Нужны независимый pentest и заполненный ASVS L2 checklist перед заявлением о готовности
   работать с финансовыми данными.

## Практический порядок доведения до production

1. Перенести web-сессию из browser storage в HttpOnly-cookie/BFF; добавить CSRF и управление
   активными устройствами.
2. Перевести runtime на PostgreSQL в закрытой сети, включить шифрование томов и backup,
   проверить restore и повторное применение удалений.
3. Вынести rate limit и блокировки входа в общее хранилище; добавить MFA/step-up для экспорта,
   удаления и подключения источника.
4. Настроить secret manager, ротацию, централизованный audit trail без финансовых payload,
   алерты и runbook инцидента.
5. Зафиксировать сроки хранения, роли доступа и режим обработки реальных данных с оператором;
   затем провести ASVS L2 review и внешний pentest.
