Разделы 13.2–13.4, 19, 26.1 ТЗ. Зелёная сборка подтверждает инженерные проверки,
а не точность на реальной популяции и не готовность банковского пилота.

## Обязательные автоматические проверки

`ruff check .`, `ruff format --check .`, mypy strict, весь pytest, TypeScript,
клиентские unit-тесты, web/Android/iOS export, миграции SQLite/PostgreSQL,
OpenAPI без расхождения и Docker Compose smoke. CI не должен пропускать эти ошибки.

Покрываемые синтетические ситуации (не путать с четырьмя выбираемыми UX-профилями):
обычная зарплата, задержка зарплаты, нулевой баланс, внутренний перевод, повторный
импорт, кредитка/погашение, возврат, отказ смешанной валюте, отмена подписки,
нерегулярный доход, короткая история, отсутствие обязательств. Финансовые инварианты
проверяются также property-based тестами, API — контрактными и интеграционными тестами.

## Дополнения этапа 5

- IDOR и SQL-подобные идентификаторы; экспорт только своих данных; удаление всех
  связанных записей; отзыв/истечение сессий и согласий; очистка старых демо-профилей.
- Одинаковый CSV в разных счетах; конфликт повторного Idempotency-Key.
- Неполный CSV маркируется как неполный. Источники операций участвуют в оценке
  качества, даже если исходный источник счёта — демо или ручной ввод.
- CSV в демо означает смешанные данные: отображается ограничение, свежесть
  проверяется относительно текущего времени, прогноз перестаёт замораживать дату демо.
- Отрицательная длина истории исключена. Несколько источников используют
  консервативное начало общего периода, а не историю самого старого счёта.
- Мок банка: все страницы, дубли, частичный ответ, сбой на второй странице с откатом,
  повтор после сбоя, задержанное обновление, запрет старого снимка, отзыв согласия.
- Формулировка «без риска» заменена расчётным лимитом при выбранном риске:
  вероятность модели не равна гарантии.

## Проверка интерфейса

21.10.2026 в браузере проверены: запуск демо → главный прогноз → учебный банк →
явное разрешение → 483 новых операции → повтор с 0 новыми/503 пропущенными →
сообщение о сбое → отзыв и блокировка кнопки → экспорт JSON → выход.
При визуальной проверке найден и исправлен нечитаемый статус экспорта в тёмной теме.
Удаление данных проверено интеграционными тестами; браузерный destructive E2E не заявляется.

## Оставшиеся условия приёмки

Дополнение итерации 5.5: серверные проверки Free/Plus и переключение демо
реализованы (`docs/plans.md`). Android APK/эмуляторный E2E запускаются отдельным
workflow (`docs/mobile-verification.md`); подтверждённый результат записывается в отчёт 5.5.

- Сквозной прогон на физическом устройстве — **не выполнен**. Для Android добавлен
  standalone APK и эмуляторный E2E без аккаунта Expo. Его подтверждённый результат
  смотрите в отчёте 5.5; Hermes export сам по себе эту проверку не заменяет.
  EAS-раздача и подписанный iOS-релиз требуют отдельной настройки аккаунтов команды.
- 20–30 интервью, реальная история с добровольным согласием, метрики удержания,
  полезности уведомлений и калибровки — не собраны; выдуманных значений нет.
- Промышленный контур: HTTPS, шифрование БД/бэкапов, восстановление после удаления,
  общий rate limiter, контроль исходящих соединений, аудит зависимостей и доступов.
- У вероятностной модели сохраняются ограничения из ADR-0005; проценты пользователю
  не показываются. Выводы бэктеста относятся только к синтетике.

Выкладку в банковский пилот считать заблокированной до закрытия инфраструктурных
условий. Дальше по плану — этап 6: on-prem-профиль, пилот и материалы защиты,
с явной фиксацией перечисленных ограничений.
