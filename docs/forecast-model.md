# Модели прогноза: `mc-0.3` и `baseline-0.2`

По умолчанию работает **`mc-0.3`** — симуляция Монте-Карло (уровень 2 из 23.1):
`packages/forecast_core/src/forecast_core/probabilistic.py`, решения — в ADR-0005. На каждой
из 1000 траекторий:
- дневные траты разыгрываются бутстрепом по дню недели;
- крупные разовые покупки случаются с исторической частотой;
- доходы приходят с их вероятностью и в пределах окна дат;
- неточные платежи берут сумму из диапазона.

Случайные потоки привязаны к seed, номеру траектории и стабильному идентификатору события.
Поэтому перестановка записей во входе и сдвиг одного дохода не меняют случайные траты или
исходы остальных событий; сравнение «до/после» измеряет именно эффект сценария.

Уровень риска — по вероятности нарушения резерва на горизонте (high ≥ 0,5, medium ≥ 0,1).
Безопасная сумма считается строго по формуле 9.4.

Вероятности есть в API, но в интерфейсе не показываются: модель откалибрована только на
синтетике (`docs/backtest/baseline.md`). При истории короче 4 недель используется
детерминированная `baseline-0.2`, описанная ниже. Она же служит эталоном сравнения.

---

## `baseline-0.2`

Код: `packages/forecast_core/src/forecast_core/baseline.py`. API: `POST /api/v1/forecasts`.

## Что считается

Для каждого дня горизонта (1–90 дней, по умолчанию 30) — доступный ликвидный остаток в трёх
сценариях:

```
B_t = B_0 + Σ I_i − Σ O_i − Σ V_i        (раздел 9.1)
```

| Слагаемое | Откуда | p50 (базовый) | p10 (пессимистичный) | p90 (оптимистичный) |
|-----------|--------|---------------|----------------------|---------------------|
| `B_0` | ликвидные счета: дебет, наличные, накопительный; без кредитных лимитов, вкладов и блокировок | — | — | — |
| `I` доходы | `income_events`, повторы по календарю | середина диапазона в первый день окна, если вероятность ≥ 0,5 | минимум в последний день окна, если вероятность ≥ 0,9 | максимум в первый день, если вероятность ≥ 0,3 |
| `O` обязательства | `obligations` без отменённых, 31-е → последний день месяца | сумма | верхняя граница диапазона | нижняя граница |
| `V` повседневные траты | история за 91 день | взвешенное среднее по дню недели и устойчивой фазе после дохода | + отклонение 90-го перцентиля сумм за k дней | − отклонение 10-го перцентиля |

Свежая история весит больше старой с периодом полураспада 56 дней только при явном тренде:
последние четыре недели должны отличаться от предыдущих минимум на 50 %, а направление
изменения — совпадать во всех семи днях недели. Иначе используется обычное среднее без
recency weighting. Фаза денежного цикла также применяется не автоматически. Нужны минимум
шесть наблюдений, регулярный график поступлений, отличие не меньше 50 % и одинаковое
направление эффекта не менее чем в трёх доходных циклах; затем фазовая оценка сглаживается с более устойчивой оценкой дня
недели. Если доказательств нет, модель откатывается к дню недели.

В `mc-0.3` бутстреп использует веса свежести только при подтверждённом тренде. Узкий фазовый пул включается только после
той же проверки устойчивости. Сравнительная модель B с медианой остаётся без этих признаков,
чтобы бэктест не подменял baseline новой логикой.

Платёж по кредитке (`kind = credit_card`) увеличивается на средние дневные траты по карте до даты
погашения (раздел 9.5). Сами покупки по кредитке в ликвидные траты не входят, поэтому двойного
учёта нет (инвариант 23.2.2).

### Что исключается из модели трат (раздел 9.2)

Переводы между своими счетами, возвраты, погашения кредитки, оплаты обязательств (по категории),
операции не в статусе `posted` и разовые покупки дороже `max(10 000 ₽, 15 × медиана покупки)`.
Исключённые крупные покупки отмечаются флагом `large_expenses_excluded`.

## Риск

- **high** — базовый сценарий опускается ниже резерва `R` (раздел 9.1: `B_t < R_t`);
- **medium** — ниже резерва опускается только пессимистичный сценарий;
- **low** — ни один из сценариев не опускается ниже резерва.

Причины (`drivers`): крупнейшие обязательства до даты риска, повседневные траты до неё,
сценарная покупка, ближайший доход после даты риска. Текст объяснения собирается по шаблону
(раздел 9.6) без LLM.

**Вероятностей нет.** `baseline_risk`, `scenario_risk` и `risk_probability` возвращаются как
`null`, `quality.confidence = illustrative`. Числа вероятностей появятся вместе с
Монте-Карло-симуляцией и калибровкой на этапе 4 (раздел 9.3). Показывать проценты без
калибровки запрещено.

## Сценарии (US-04, US-05)

`scenario.type = expense` — гипотетическая покупка в выбранный день. `income_shift` — сдвиг
дохода на ±31 день. История операций не меняется: сценарий — копия входного снимка с
добавленным событием (раздел 7.6).

## Безопасная сумма и сравнение сценариев (раздел 9.4, 11.3)

Разовая покупка `x` в день `d` сдвигает все три сценария вниз ровно на `x` начиная с `d`, поэтому
максимальная покупка без нарушения резерва считается точно, без перебора:

```
x* = min_{t ≥ d} (B_t − R_t)
```

`safe_to_spend` в каждом прогнозе — диапазон: `base_minor` (базовый сценарий не опускается ниже
резерва) и `conservative_minor` (не опускается даже пессимистичный). При недостатке данных
`available = false`, и клиент сумму не показывает (раздел 9.4).

`POST /api/v1/scenarios` пересчитывает базу и сценарий на текущих данных с параметрами
базового расчёта и возвращает оба прогноза и разницу: минимум, уровень и дату риска, число дней
ниже резерва, текст «что будет, если…». Если данные изменились после базового расчёта, база
пересчитывается, и это видно по `base_recomputed: true`.

## Почему среднее, а не медиана

Распределение дневных трат асимметрично: в большинстве дней траты небольшие, в редкие дни —
крупные покупки. Медиана по дням недели (baseline B из раздела 15.2) систематически занижает
траты. Бэктест на синтетике (`scripts/backtest_baseline.py`, отчёт `docs/backtest/baseline.md`)
показал: среднее без аномалий даёт меньшую ошибку остатка и лучшее покрытие коридора. Выбор
сделан по out-of-time проверке, а не «из модности» (раздел 9.2). На реальных данных его нужно
подтвердить заново.

## Качество и ограничения

Флаги в `quality.flags` (тексты — в `quality.notes`): `no_history`, `short_history`
(коридор ×1,5), `large_expenses_excluded`, `unconfirmed_events`, `partial_coverage`,
`card_spending_accrual`, `scenario_applied`, `stale_data` (данные старше 3 дней; тогда
`confidence = insufficient`).

Нерегулярные доходы (фрилансеры) пока учитываются только через ожидаемые поступления, которые
внёс пользователь. Модели нерегулярного дохода — после MVP (FR-21).
