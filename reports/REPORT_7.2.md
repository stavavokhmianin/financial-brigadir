# REPORT 7.2 — Проверка прогноза на данных пилота

- **Этап:** 7 (после финала, 16.2: «реальные добровольные данные, проверка прогноза»)
- **Роль по 16.1:** C (+A)
- **Коммит:** [`c6aab91`](https://github.com/stavavokhmianin/financial-brigadir/commit/c6aab91) в `step4ik`

## Зачем

Критерий перехода из плана развития: модель лучше календаря (A) на реальной истории. Бэктест
умеет это проверять только на синтетике, где будущее известно генератору. Для пилота нужен
инструмент, который сравнит показанный участнику прогноз с тем, что потом случилось.

## Как устроено

Отдельного сбора данных не нужно. Каждый расчёт уже сохраняет остатки на момент расчёта,
поэтому каждый следующий заход участника — это наблюдение факта для прежних прогнозов.

- **Факт на конец дня X−1** — остаток из самого раннего расчёта дня X. Расчёты с пометкой
  «данные устарели» не используются, день считается в часовом поясе участника.
- **Прогноз** — базовые расчёты, сделанные раньше. Сценарии «что если» не оцениваются.
- **Календарная модель A.** При каждом базовом прогнозе на том же входе считается и
  сохраняется её путь: `forecast_runs.reference`, миграция 0008. Пустая история трат даёт
  ровно модель A из бэктеста — это проверено.
- **Отчёт оператора** `python -m app.cli pilot-report` выводит Markdown:
  - MAE модели и календаря по горизонтам 1–7, 8–14, 15–30, 31–90 дней;
  - смещение;
  - доля факта в коридоре p10–p90;
  - дни ниже резерва: увидел ли их коридор или базовый прогноз;
  - дни ложной тревоги.
- **Приватность.** В отчёте только агрегаты. Если участников меньше трёх, детализации нет;
  строки горизонтов, где участников меньше трёх, не выводятся. Демо-профили по умолчанию
  не учитываются.

## Ограничения

Наблюдения есть только в дни, когда участник открывал приложение. Поэтому оценка поимки
разрывов — нижняя граница, а не полная картина, и отчёт это прямо пишет. Остаток на момент
утреннего захода считается остатком на конец предыдущего дня — это приближение.
